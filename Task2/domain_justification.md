# Обоснование разделения системы на домены

## Выделенные домены

| Домен | Владелец | Ключевые сущности | Обоснование выделения |
|---|---|---|---|
| **Клиники** | Подразделение клиник | Пациенты, персонал, расписание, инвентарь, медицинские данные | Основной бизнес компании. Специфичные требования к безопасности (врачебная тайна, 152-ФЗ). Собственный жизненный цикл разработки. |
| **Финтех** | Финтех-компания (банковская лицензия) | Кредиты, счета, платежи, транзакции, скоринг | Регуляторные требования ЦБ. Банковская лицензия требует изоляции данных. Собственный стек (Golang, Java). |
| **ИИ-сервисы** | Компания ИИ-сервисов | ML-модели, обучающие данные, результаты диагностики | Специализированный стек (Python, GPU). Работа с обезличенными данными. Быстрый цикл экспериментов. |
| **Головной офис** | Головной офис | Консолидированная отчётность, KPI, управление, data governance | Потребитель данных из всех доменов. Определяет политики и стандарты. |
| **Платформа данных** | Cross-domain команда | Data Lake, аналитическое хранилище, ETL, событийная шина, BI | Обеспечивает интеграцию между доменами и аналитику. Предоставляет инфраструктуру как сервис. |

## Принципы разделения

### 1. Bounded Context (ограниченный контекст)

Каждый домен определён вокруг конкретного бизнес-контекста с чётко определёнными границами:

- **Клиники**: всё, что связано с оказанием медицинских услуг — пациенты, врачи, записи, инвентарь.
- **Финтех**: финансовые операции — кредиты, платежи, скоринг. Отдельный юридический контур.
- **ИИ**: машинное обучение и анализ данных. Работает с обезличенными копиями, не хранит персональные данные.
- **Головной офис**: управление и контроль — KPI, отчётность, governance.

### 2. Организационное соответствие (Закон Конвея)

Структура доменов отражает структуру компании:

```
«Будущее 2.0»
├── Головной офис           → Домен: Головной офис
├── Клиники                 → Домен: Клиники
├── ИИ-компания             → Домен: ИИ-сервисы
└── Финтех-компания (банк)  → Домен: Финтех
         Платформа данных    → Кросс-доменная команда
```

Каждое подразделение получает автономию в развитии своего домена: собственный бэклог, свои релизные циклы, свой стек технологий.

### 3. Регуляторные требования

Разделение обусловлено юридическими и регуляторными требованиями:

- **Медицинские данные**: 152-ФЗ (персональные данные), врачебная тайна, требования Минздрава. Медицинские карты и истории болезней не покидают домен клиник.
- **Финансовые данные**: требования ЦБ РФ к банкам, PCI DSS для платёжных данных. Финансовый контур изолирован.
- **Данные ИИ**: работа только с обезличенными данными. Результаты анализа возвращаются в домен клиник.

## Преимущества для бизнеса

### Ускорение вывода продуктов (Time-to-Market)

| Текущее состояние | Целевое состояние |
|---|---|
| Любое изменение требует модификации DWH | Доменная команда меняет свой сервис независимо |
| Одна команда DWH — узкое место | Параллельная разработка в каждом домене |
| Релизный цикл 1-3 месяца | Независимые релизы каждого домена (недели) |
| Координация изменений через ESB | Событийная интеграция — слабая связанность |

**Ожидаемое ускорение**: с 1-3 месяцев до 1-2 недель для изменений внутри одного домена.

### Снижение зависимости от DWH

| Аспект | Было | Стало |
|---|---|---|
| Бизнес-логика | В DWH (SQL-процедуры) | В доменных сервисах |
| Данные | Всё в одном DWH | У каждого домена своя БД |
| Интеграция | Через DWH и ESB | Через Kafka (событийно) |
| Масштабирование | Вертикальное (мощнее сервер) | Горизонтальное (больше инстансов) |
| Новый бизнес | Новые таблицы и процедуры в DWH | Новый домен со своей БД |

### Возможность отдельного развития направлений

Каждый домен:

1. **Имеет собственный стек технологий** — финтех на Golang/Java, ИИ на Python, клиники на Java/Kotlin. Нет зависимости от SQL Server 2008.

2. **Владеет своими данными** — домен полностью контролирует схему своей БД. Изменения в схеме не затрагивают другие домены.

3. **Интегрируется через контракты** — события в Kafka имеют определённую схему (Avro/Protobuf). Пока контракт соблюдается, внутренние изменения домена не влияют на остальных.

4. **Масштабируется независимо** — если финтех-направление растёт быстрее, его домен получает больше ресурсов без влияния на ИИ и клиники.

### Интеграция новых бизнес-направлений

Подключение фармацевтической компании или производителя электроники:

1. Создаётся новый домен со своей БД и сервисами.
2. Домен подключается к Kafka — публикует события и подписывается на нужные.
3. Платформа данных настраивает ETL для нового домена.
4. На портале самообслуживания появляются новые данные.

**Не требуется**: менять DWH, менять ESB, менять другие домены.

```
Время интеграции нового бизнес-направления:
  Было (через DWH):  3-6 месяцев
  Стало (новый домен): 2-4 недели
```

## Взаимодействие между доменами

Домены не обращаются напрямую к базам данных друг друга. Взаимодействие идёт через:

1. **Событийная шина (Kafka)** — асинхронный обмен событиями. Основной способ интеграции.
2. **API Gateway** — синхронные запросы через REST API, когда нужен немедленный ответ.
3. **Платформа данных** — агрегирует данные из всех доменов для аналитики и отчётности.

Это обеспечивает **слабую связанность** (loose coupling) и **высокую связность** (high cohesion) внутри каждого домена.
