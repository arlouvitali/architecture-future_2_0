# Обоснование конфигурации инфраструктуры

## 1. Выбор ресурсов и параметров

### Сетевая архитектура

**Три подсети (публичная, приватная для приложений, приватная для данных)**:
- Сегментация трафика по принципу минимальных привилегий.
- Публичная подсеть содержит только те компоненты, которым нужен доступ из интернета (бастион, API Gateway).
- Базы данных и Kafka изолированы в отдельной подсети — доступ только из подсети приложений.
- Дополнительная подсеть в зоне `ru-central1-b` обеспечивает отказоустойчивость для managed-сервисов, требующих мульти-зонального развёртывания.

**NAT Gateway**:
- Приватные подсети не имеют публичных IP, но им нужен доступ в интернет для обновлений ОС, скачивания Docker-образов и т.д.
- NAT Gateway обеспечивает исходящий трафик без необходимости давать публичный IP каждой VM.
- Это безопаснее, чем NAT Instance, и не требует обслуживания.

**Security Groups**:
- Три группы: для публичного, прикладного и data-сегментов.
- Принцип deny by default — только разрешённые порты и источники.
- SSH к бастиону ограничен CIDR администратора.

### Виртуальные машины

| VM | CPU | RAM | Диск | Обоснование |
|---|---|---|---|---|
| **Bastion** | 2 | 2 ГБ | 15 ГБ SSD | Минимальные ресурсы — только SSH-прокси. Не выполняет вычислений. |
| **API Gateway** | 4 | 8 ГБ | 30 ГБ SSD | Обрабатывает все входящие запросы. 4 ядра для Kong + rate limiting. 8 ГБ для кэширования и SSL-терминации. |
| **Portal + BI** | 4 | 8 ГБ | 50 ГБ SSD | React-приложение + Superset. Superset требует RAM для рендеринга дашбордов и кэширования запросов. |
| **Keycloak** | 2 | 4 ГБ | 20 ГБ SSD | Keycloak — Java-приложение. 4 ГБ RAM достаточно для ~1000 одновременных сессий. |
| **Airflow** | 4 | 16 ГБ | 100 ГБ SSD | Оркестрация ETL: параллельные DAG, воркеры, обработка данных. 16 ГБ для параллельных задач. 100 ГБ для логов и временных данных. |

Все VM используют платформу `standard-v3` (Intel Ice Lake) — оптимальное соотношение цена/производительность. Диски — `network-ssd` для предсказуемой latency.

### Managed PostgreSQL

- **2 хоста** в разных зонах — автоматическая репликация и failover. Отказ одной зоны не приводит к потере данных.
- **s2.micro** (2 vCPU, 8 ГБ RAM) — достаточно для начального этапа. Масштабирование по мере роста нагрузки.
- **50 ГБ SSD** — начальный размер. Managed PostgreSQL поддерживает онлайн-расширение.
- **Раздельные кластеры для клиник и финтех** — регуляторные требования (ЦБ, 152-ФЗ) предписывают изоляцию данных.

### Managed Kafka

- **3 брокера** — минимум для отказоустойчивого кластера. Кворум при потере одного брокера.
- **s2.medium** (4 vCPU, 16 ГБ RAM) — Kafka активно использует RAM для page cache.
- **100 ГБ SSD на брокер** — хранение событий за 7 дней (retention period по умолчанию).
- **2 зоны** — отказоустойчивость кластера.
- **Replication factor = 2** для топиков — каждое сообщение хранится на 2 брокерах.

### Managed ClickHouse

- **s2.medium** (4 vCPU, 16 ГБ RAM) — ClickHouse хранит данные колоночно и активно использует RAM для агрегаций.
- **200 ГБ SSD** — аналитическое хранилище для агрегированных данных из всех доменов. ClickHouse сжимает данные в 5-10 раз.
- **2 хоста** в разных зонах — отказоустойчивость.

### Object Storage (S3)

- **Два бакета** (raw и curated) — разделение по этапам обработки данных.
- **Версионирование** включено — защита от случайного удаления.
- **Lifecycle policy** — перемещение данных старше 90 дней в холодное хранилище (экономия ~50% стоимости хранения).

## 2. Причины использования декларативного подхода

### Terraform vs. императивные скрипты

| Критерий | Декларативный (Terraform) | Императивный (bash/Ansible) |
|---|---|---|
| **Описание состояния** | «Что должно быть» | «Что нужно сделать» |
| **Идемпотентность** | Встроенная — повторный apply не создаст дубликаты | Нужно реализовывать вручную |
| **Планирование** | `terraform plan` показывает изменения до применения | Нет предварительного просмотра |
| **Граф зависимостей** | Автоматически определяет порядок создания | Ручное управление порядком |
| **Состояние** | Хранит state — знает текущее состояние | Нет state — не знает, что уже создано |
| **Drift detection** | Обнаруживает расхождения с реальной инфраструктурой | Не обнаруживает |

### Преимущества для «Будущее 2.0»

1. **Предсказуемость**: `terraform plan` позволяет увидеть все изменения до их применения. Критично для production-среды с медицинскими и финансовыми данными.

2. **Аудит**: вся конфигурация в Git. История изменений прозрачна. Важно для соответствия регуляторным требованиям.

3. **Модульность**: конфигурацию легко разбить на модули по доменам. Каждая команда управляет своей частью инфраструктуры.

4. **Безопасность**: sensitive-переменные маркированы, secrets не попадают в state (при правильной конфигурации backend).

## 3. Infrastructure as Code — воспроизводимость и масштабируемость

### Воспроизводимость

**Проблема**: в текущей on-premise инфраструктуре «Будущего 2.0» настройка серверов выполняется вручную. Нет гарантии, что production и staging идентичны.

**Решение с IaC**:
- Одна конфигурация Terraform описывает всю инфраструктуру.
- `terraform apply` воссоздаёт идентичное окружение за минуты.
- Тестовое, staging и production окружения создаются из одного кода с разными `.tfvars`.
- Disaster recovery: при потере инфраструктуры — `terraform apply` восстанавливает всё из кода.

```
environments/
├── dev.tfvars       # Минимальные ресурсы для разработки
├── staging.tfvars   # Приближенные к production
└── prod.tfvars      # Полноценные ресурсы production
```

### Масштабируемость

**Горизонтальное масштабирование**: при подключении нового бизнес-направления (фармацевтика, электроника) достаточно добавить ресурсы в конфигурацию Terraform:

```hcl
resource "yandex_mdb_postgresql_cluster" "pharma_db" {
  name = "pharma-pg-cluster"
  # ... аналогично clinic_db и fintech_db
}

resource "yandex_mdb_kafka_topic" "pharma_events" {
  name = "pharma.events"
  # ...
}
```

Одна команда `terraform apply` создаёт всю инфраструктуру для нового домена.

**Вертикальное масштабирование**: изменение `resource_preset_id` или `disk_size` в переменных — managed-сервисы масштабируются без даунтайма.

### Преимущества IaC для «Будущего 2.0»

| Аспект | Без IaC | С IaC (Terraform) |
|---|---|---|
| Создание среды | Дни / недели | Минуты |
| Воспроизводимость | Ручная документация | Код = документация |
| Аудит изменений | Логи доступа | Git history |
| Новый домен | Ручная настройка серверов, БД, сетей | `terraform apply` |
| DR (Disaster Recovery) | Ручное восстановление | Автоматическое из кода |
| Compliance | Ручные проверки | Policy as Code (tfsec, Sentinel) |
