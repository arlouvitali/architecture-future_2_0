# Обоснование планируемых изменений

## Этап 1: Фундамент облачной инфраструктуры

### Зачем

Без облачной инфраструктуры невозможно масштабирование. Текущее on-premise решение требует недели на закупку и установку оборудования. Облако позволяет выделить ресурсы за минуты.

### Влияние на бизнес

| Аспект | Влияние |
|---|---|
| **Снижение затрат** | Отказ от капитальных затрат (CAPEX) на серверы в пользу операционных (OPEX). Оплата по потреблению — экономия 30-40% на инфраструктуре. |
| **Масштабирование** | Ресурсы выделяются за минуты вместо недель. Автомасштабирование при пиковых нагрузках. |
| **Отказоустойчивость** | Геораспределённое развёртывание, автоматическое резервное копирование. SLA облачного провайдера 99.95%. |
| **Скорость разработки** | IaC (Terraform) позволяет воссоздать среду за минуты. Быстрое создание тестовых и staging-окружений. |

### Риски при отказе

Без облачной инфраструктуры компания не сможет масштабироваться для новых бизнес-направлений в рамках заявленных сроков. Закупка оборудования для каждого нового домена занимает 2-3 месяца.

---

## Этап 2: Выделение доменов

### Зачем

DWH является узким местом для всех подразделений. Любое изменение в финтехе требует изменений в DWH, что влияет на клиники и ИИ. Регуляторы требуют изоляции медицинских и финансовых данных.

### Влияние на бизнес

| Аспект | Влияние |
|---|---|
| **Скорость вывода продуктов** | Финтех-команда релизит без согласования с DWH-командой. Цикл с 1-3 месяцев до 1-2 недель. |
| **Качество сервиса** | Сбой в финтехе не влияет на клиники. Изоляция повышает стабильность каждого направления. |
| **Регуляторное соответствие** | Медицинские данные изолированы (152-ФЗ). Финансовые данные в отдельном контуре (требования ЦБ). |
| **Возможность масштабирования** | Каждый домен масштабируется независимо. Финтех растёт — добавляем ресурсы только финтеху. |

### Риски при отказе

Без разделения на домены компания не сможет: (1) обеспечить требования регуляторов по изоляции данных; (2) интегрировать новые бизнес-направления без изменений в DWH; (3) обеспечить независимое развитие подразделений.

## Этап 3: Платформа данных

### Зачем

Текущий DWH на SQL Server 2008 не справляется с объёмами данных (сотни ТБ). Формирование отчётов занимает часы. Бизнес теряет скорость в принятии решений.

### Влияние на бизнес

| Аспект | Влияние |
|---|---|
| **Скорость принятия решений** | Отчёты формируются за секунды (ClickHouse) вместо часов (SQL Server). Руководители получают актуальные данные в режиме реального времени. |
| **Качество данных** | dbt обеспечивает тестирование и версионирование трансформаций. Data governance определяет стандарты качества. |
| **Снижение затрат** | S3 для холодных данных обходится в 10-50 раз дешевле, чем хранение в SQL Server. |
| **Гибкость** | Новый домен подключается к платформе данных через Kafka + ETL за дни, а не месяцы. |

### Риски при отказе

Без новой платформы данных портал самообслуживания будет работать поверх медленного DWH. Отчёты продолжат формироваться часами. Руководство не получит инструмент для оперативных решений.

---

## Этап 4: Портал самообслуживания

### Зачем

Это ключевое требование руководства. Сотрудник должен получать отчёт по любым срезам в пределах своего уровня доступа и конструировать собственные отчёты.

### Влияние на бизнес

| Аспект | Влияние |
|---|---|
| **Операционная эффективность** | Аналитики не зависят от IT-команды. Запрос отчёта — минуты вместо дней. |
| **Скорость принятия решений** | Руководители видят актуальные KPI на дашбордах в реальном времени. |
| **Масштабируемость** | Портал поддерживает любое количество бизнес-направлений. Новый домен = новый раздел на портале. |
| **Безопасность** | RBAC через Keycloak — каждый видит только данные своего уровня доступа. |

### Риски при отказе

Без портала бизнес-пользователи продолжают зависеть от IT для получения отчётов. Время получения данных для принятия решений остаётся неприемлемо долгим.

---

## Этап 5: Масштабирование и интеграция партнёров

### Зачем

Компания планирует интегрировать фармацевтические компании и производителя электроники. Архитектура должна поддерживать быстрое подключение новых бизнесов.

### Влияние на бизнес

| Аспект | Влияние |
|---|---|
| **Выручка** | Новые бизнес-направления увеличивают выручку экосистемы. Быстрая интеграция ускоряет получение дохода. |
| **Time-to-market** | Подключение партнёра через Kafka за 2-4 недели вместо 3-6 месяцев через DWH. |
| **Конкурентное преимущество** | Экосистема «медицина + финансы + фармацевтика + оборудование» создаёт уникальное предложение на рынке. |
| **Снижение затрат** | Единая платформа данных для всех направлений снижает стоимость аналитики для каждого бизнеса. |

### Риски при отказе

Без масштабируемой архитектуры каждый новый партнёр потребует месяцев интеграции и изменений в DWH. Компания теряет конкурентное преимущество в скорости расширения экосистемы.
