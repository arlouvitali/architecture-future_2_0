# Анализ проблемных мест и их приоритизация

## Проблемные места текущей архитектуры

| # | Проблема | Описание | Страдающие бизнес-сценарии | Влияние |
|---|---|---|---|---|
| 1 | **DWH — единая точка отказа и узкое место производительности** | Все данные (клиенты, финансы, персонал, инвентарь) и значительная часть бизнес-логики сосредоточены в одном DWH на SQL Server 2008. Объём данных — сотни ТБ. Формирование сложных отчётов занимает часы. | Управленческая отчётность, принятие решений, аналитика по всем направлениям | Критическое |
| 2 | **Устаревший технологический стек (SQL Server 2008, PowerBuilder)** | SQL Server 2008 — end-of-life с 2019 года, нет обновлений безопасности. PowerBuilder — устаревшая технология с минимальным рынком специалистов. | Безопасность данных (медицинских и финансовых), развитие клиентского интерфейса, наём персонала | Критическое |
| 3 | **Тесная связанность систем через ESB** | Apache Camel используется как центральная точка маршрутизации, трансформаций, форматно-логического контроля (ФЛК) и интеграции. В результате изменение контракта или бизнес-правил одного сервиса требует доработки общей шины и повышает связанность всех систем. | Интеграция новых бизнес-направлений, скорость вывода продуктов (time-to-market), независимое развитие подразделений | Высокое |
| 4 | **Отсутствие портала самообслуживания (витрины данных)** | Нет единой точки входа для бизнес-пользователей. Для получения отчёта аналитик зависит от IT-команды и от скорости DWH. | Скорость принятия решений, операционная эффективность, автономность бизнес-пользователей | Высокое |
| 5 | **Бизнес-логика внедрена в DWH** | Финтех- и ИИ-логика реализована внутри DWH. Подключение нового бизнеса требует изменений в DWH. | Масштабирование (фармацевтика, электроника), независимость подразделений, time-to-market | Высокое |
| 6 | **On-premise инфраструктура без возможности эластичного масштабирования** | Всё оборудование физическое. Масштабирование требует закупки и установки серверов — недели/месяцы. | Масштабирование для новых бизнесов, пиковые нагрузки, отказоустойчивость | Среднее |
| 7 | **Power BI с кастомизациями поверх DWH** | BI-система завязана на структуру DWH. Кастомизации усложняют миграцию и развитие. | Аналитическая отчётность, гибкость визуализации | Среднее |
| 8 | **Недостаточная изоляция медицинских и финансовых данных** | Все данные в одном DWH. Регуляторные требования к медицинским (152-ФЗ, врачебная тайна) и финансовым (банковская лицензия, ЦБ) данным требуют разделения. | Соответствие регуляторам, безопасность данных, банковская лицензия | Критическое |
| 9 | **Отсутствие событийной архитектуры** | Интеграция синхронная через ESB. Нет возможности реального реагирования на события (real-time analytics, алерты). | Real-time аналитика, ИИ-диагностика в реальном времени, финтех-транзакции | Среднее |

## Приоритизация методом MoSCoW

### Must Have (Критично — без этого бизнес не достигнет целей)

| Проблема | Обоснование приоритета | Связь с целями бизнеса |
|---|---|---|
| **Миграция с SQL Server 2008** | End-of-life продукт без обновлений безопасности. Банковская лицензия и медицинские данные требуют актуальных систем. Регуляторные риски. | Безопасность, соответствие требованиям ЦБ и 152-ФЗ |
| **Разделение данных по доменам (изоляция медицинских и финансовых данных)** | Регуляторы требуют разделения. Банковская лицензия предполагает отдельный контур для финансовых данных. | Комплаенс, банковская лицензия, врачебная тайна |
| **Вынос бизнес-логики из DWH в доменные сервисы** | Без этого невозможно интегрировать новые направления (фармацевтика, электроника) без изменения DWH. | Масштабирование бизнеса, time-to-market |

### Should Have (Важно — значительно улучшит бизнес-процессы)

| Проблема | Обоснование приоритета | Связь с целями бизнеса |
|---|---|---|
| **Создание портала самообслуживания** | Ключевое требование руководства. Ускорит принятие решений с часов до минут. | Скорость принятия решений, операционная эффективность |
| **Замена ESB на событийную архитектуру** | Переход убирает центральную "умную шину": Kafka используется как транспорт событий, а проверки и преобразования распределяются по доменам и адаптерам. | Независимое развитие подразделений, масштабирование |
| **Миграция в облако** | Обеспечит эластичное масштабирование и снизит затраты на поддержку оборудования. | Масштабирование, снижение затрат, отказоустойчивость |

### Could Have (Желательно — повысит качество, но не блокирует основные цели)

| Проблема | Обоснование приоритета | Связь с целями бизнеса |
|---|---|---|
| **Замена PowerBuilder на веб-интерфейс** | Улучшит UX операторов и упростит наём. Но текущий PowerBuilder работает. | Удобство работы операторов, наём специалистов |
| **Замена Power BI на Superset/аналог** | Снизит зависимость от вендора и DWH. Но Power BI может работать с новым хранилищем. | Гибкость BI, снижение лицензионных затрат |
| **Real-time аналитика** | Позволит реагировать на события в реальном времени. Но batch-аналитика покрывает основные потребности. | Качество медицинских и финансовых сервисов |

### Won't Have (Не в этом году)

| Проблема | Обоснование | Когда планируется |
|---|---|---|
| **Полный отказ от Legacy DWH** | Миграция сотен ТБ данных — длительный процесс. DWH остаётся как источник исторических данных. | Через 2-3 года |
| **Полная реализация Data Mesh** | Требует зрелости доменных команд и data governance. На первом этапе — доменная архитектура с централизованной платформой данных. | Через 1.5-2 года |

```
                │  2. Изоляция медицинских и   │  6. Real-time аналитика      │
                │     финансовых данных        │                              │
                │  3. Вынос бизнес-логики      │                              │
                │     из DWH                   │                              │
                │                              │                              │
                ├──────────────────────────────┼──────────────────────────────┤
                │                              │                              │
    НЕ ВАЖНО    │  7. Замена ESB на            │  8. Замена PowerBuilder      │
                │     событийную архитектуру   │  9. Замена Power BI          │
                │                              │                              │
                │                              │                              │
                └──────────────────────────────┴──────────────────────────────┘
```

**Квадрант I (Важно + Срочно)** — выполнять немедленно. Регуляторные риски и блокеры для развития.

**Квадрант II (Важно + Не срочно)** — запланировать и выполнять системно. Стратегические инициативы.

**Квадрант III (Не важно + Срочно)** — делегировать или совместить с другими задачами.

**Квадрант IV (Не важно + Не срочно)** — отложить на следующий цикл.
